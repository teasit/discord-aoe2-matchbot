# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A Discord bot that watches the Relic Link (World's Edge) API for live Age of Empires II: DE matches involving tracked Steam users and posts a match summary (teams, ratings, win rates, spectate link) to subscribed Discord channels. Slash commands: `/join`, `/leave`, `/add <player_id>`, `/remove <player_id>`, `/list`, `/set_elo_max_diff <max_diff>`, `/set_smurf_max_diff <max_diff>` (both per channel, 0 = off), `/ban <player_id> [comment]`, `/unban <player_id>`. `<player_id>` is a SteamID64 or a Relic Link profile ID, told apart by length (17 digits = SteamID64) in `AoeMatchBot._resolve_player`; tracking is stored by SteamID64, so profiles without a Steam account can be banned but not tracked. All command replies go through `AoeMatchBot._reply`, which deletes them after `MATCHBOT_COMMAND_DELETE_AFTER` seconds (default 10, 0 = keep).

API references: https://wiki.librematch.org/rlink/community/start and https://github.com/librematch/librematch-rlink_client/blob/main/openapi.yaml

## Commands

Python 3.12, dependencies managed with `uv` (`uv.lock` is committed; Docker builds use `uv sync --locked`).

```bash
uv sync                                   # install deps
uv run src/aoe_matchbot.py             # run the bot
PYTHONPATH=src uv run src/matchbot/rlink/__init__.py <steam_id64>...  # debug: print lobbies of these players
PYTHONPATH=src uv run src/matchbot/maps/__init__.py [strings.txt]      # regenerate the bundled map_names.json (from Steam, or a local key-value-strings-utf8.txt)
docker compose up --build                 # run in container (single volume ./data -> /app/data)
```

There is no test suite. Lint and format with Ruff (`uv run ruff check --fix . && uv run ruff format .`, config in `pyproject.toml`, dev dependency; the Docker image sets `UV_NO_DEV=1` so it is not installed there). The devcontainer runs Ruff on save (format, import sorting, safe fixes) using the locked version from `.venv`, and Pylance "standard" type checking. CI (`.github/workflows/docker-image.yml`) builds the Docker image and pushes it to `ghcr.io/teasit/discord-aoe2-matchbot` on pushes to main (`:main`) and releases (`:latest`, `:X.Y.Z`, `:X.Y`, `:X`; `:latest` only ever points to a release); PRs only build. Releases use release-please (`.github/workflows/release-please.yml`, `release-please-config.json`, `.release-please-manifest.json`): Conventional Commit messages on main feed a release PR (version in `pyproject.toml` and `uv.lock`, `CHANGELOG.md`); merging it tags `vX.Y.Z` and the same workflow calls `docker-image.yml` to publish the versioned image (tags made with `GITHUB_TOKEN` do not trigger the tag push workflow).

Running requires `DISCORD_TOKEN`, `STEAM_USERNAME`, `STEAM_PASSWORD` as env vars; missing ones are filled from `<data dir>/.env`, then `<repo>/.env` (`/app/.env` in Docker), both gitignored. The Steam account must own AoE2:DE and have Steam Guard / email 2FA disabled (2FA is not supported); the game is never installed. No Steam Web API key is needed.

The data dir (`MATCHBOT_DATA_DIR`, default `<repo>/data`, `/app/data` volume in Docker) holds `cache/` (database, the game's `key-value-strings-utf8.txt`), `logs/` and the optional `.env` and `config.yaml`. `config.yaml` (data dir first, then repo root; `MATCHBOT_CONFIG` overrides) selects which lobby types are announced: `tracked_lobby_types` from `ranked`, `quickplay`, `empire_wars`, `custom`, `other`; default `ranked` + `quickplay`.

## Architecture

- `src/aoe_matchbot.py` — entry point and `AoeMatchBot` (`discord.Client`). Modules are imported as `matchbot.*`, which resolves because the script runs from `src/` (no package install/`src` layout config). On `on_ready` it appends `PROJECT_URL` (the GitHub repo) to the application description, the bot's "About Me", unless already present, so every instance links back to the project. In `setup_hook` it starts a watchdog: an asyncio task touches `cache/heartbeat` every 30 s (Docker `HEALTHCHECK` reads its age) and a thread exits the process (`os._exit(1)`, after logging the loop thread's stack) when the loop has not beaten for `MATCHBOT_WATCHDOG_SECONDS` (default 300, 0 = off), so `restart: unless-stopped` starts it again. On `on_ready`/`on_resumed` it (re)starts two looping asyncio tasks:
  - **authentication** — re-logs into Relic Link every `API_AUTH_RECOMMENDED_INTERVAL` (3 min); before that refreshes the map names from Steam when due (`MapNames.needs_refresh`).
  - **analysis** — every 3 s: Steam IDs → Relic profile IDs → `LobbyScanner.scan()` → filter by `Lobby.lobby_type` against the config → announce AUTOMATCH lobbies of tracked players as soon as they are matched and their map is settled (`Lobby.map_settled`, before the game starts), custom lobbies once started. Should the map of an announced match still change, the post is edited. Each post is an `Announcement` that is edited through `MatchState` MATCHED → LIVE (when the lobby gets a start time) or → DODGED (lobby closes or loses players), then LIVE → FINISHED once aoe2companion reports the result (polled every minute for up to 4 h; team colour icons become 👑 for the winners and 💀 for the losers). If the 1v1 RM rating gap between the teams' highest rated players exceeds the channel's `elo_max_diff` and a tracked player is on the weaker team, a warning thread is opened on the post (reply as fallback without thread permission). Players other than the tracked ones whose 1v1 RM rating is more than the channel's `smurf_max_diff` below their all-time high (`LeaderboardStats.highest_rating`, `row[16]` of the stat groups; `ui.smurf_gaps`) add a possible-smurf alert, and banned players in a match (global `banlist`) a "X is on the banlist" alert to the same thread in every channel.
- `matchbot/rlink` — `RelicLinkClient`, async aiohttp client for `aoe-api.worldsedgelink.com`. Auth flow: a `SteamClientWithout2FA` logs into Steam just to obtain an *encrypted app ticket* for app 813780, which is posted to `/game/login/platformlogin` to get a Relic session ID; the Steam client is then logged out. Relic sessions return 401 after ~4 min without re-login.
  - **Pre-match detection (`LobbyScanner`)**: match IDs are sequential across all lobbies, and `getAdvertisements` (≤100 ids per call) returns lobbies that have not started yet, and needs no game build (the old `findObservableAdvertisements` only lists started games and requires the exact build as `appBinaryChecksum`; it was removed together with the Wine/SteamCMD build detection). Scanning a window around the newest id finds `AUTOMATCH` lobbies (`start` = null) ~5–90 s before launch; `SESSION_MATCH_KEY` lobbies are players entering the queue. This is the same signal aoe2recs.com uses for "queuing"/"matched". The window only follows lobbies it finds, so the newest id is looked up again every minute (`RESYNC_SECONDS`, via the unauthenticated `findAdvertisements`) in case a stall let the id counter (~3 ids/s at night) run past it. Relic requests time out after 10 s (`REQUEST_TIMEOUT`). Calls carry `sessionID`/`callNum`/`lastCallTime` from `RelicLinkSession`. API responses are positional JSON arrays (`[status, payload...]`), parsed by index — e.g. `row[17]` is the player list and `row[16]` the match type id (mapped to `LobbyType` via `MATCH_TYPE_ID_TO_LOBBY_TYPE`; ids from `/community/leaderboard/getAvailableLeaderboards`, 0 = custom lobby). Matchmade lobbies briefly have an empty description before it becomes `AUTOMATCH`, so classify by match type, not description. `get_steam_player_summaries` uses Relic's unauthenticated Steam proxy (only returns users with an AoE2 profile).
  - **Maps**: the advertised map file name (`row[11]`, `Lobby.map_name`) is wrong most of the time — matchmade lobbies carry some map of the pool, custom lobbies always `"my map"` — and is never corrected. The real map is in the lobby options (`row[12]`, decoded by `parse_advertisement_options`: base64 → zlib → JSON string → base64 → count byte + uint32-length-prefixed `key:value` entries): option `10` is the game string id of the map name (`-2` = custom .rms, file name in option `11`). In fresh AUTOMATCH lobbies option `10` is provisional until option `7` turns `"1"` (`Lobby.map_settled`); verified against played maps (aoe2companion), the settled value was right in every case, the advertised name in about a third.
- `matchbot/maps` — `MapNames` resolves `Lobby.map_location_id` to a name with the game's own string table (`resources/en/strings/key-value/key-value-strings-utf8.txt`), downloaded from the Steam CDN with the bot's account (`SteamClientWithout2FA.read_depot_file`, nothing is installed), cached in `cache/` and refreshed daily or (at most hourly) when an unknown id shows up. `map_names.json` is a bundled subset (map string id ranges) used when Steam is unreachable; regenerate it after patches that add maps. `DepotClient` in `matchbot/steam` works around the `steam` library's outdated CDN code (manifest gids as dicts, manifest request codes, zstd "VSZa" chunks → `zstandard` dependency).
- `matchbot/config` — `MatchBotConfig`, loads `config.yaml`.
- `matchbot/ui` — renders posts as Discord Components V2 (`LayoutView` card: state colour, `<t:…:R>` timestamps that tick client-side, map thumbnail, teams separated by `Separator`s without team headers, per player a name row linking to AoE2 Insights (prefixed with 👑/💀 once finished) plus a code-formatted `R|T|E|Q` row below it (mobile width), legend, Spectate/Insights link buttons) and computes `elo_gap`. Card messages have no `content`; edit them with `view=`.
- `matchbot/aoe2companion` — public data.aoe2companion.com API for what Relic lacks: map images (looked up by the `MapNames` name, matched against aoe2companion's map ids and display names via `normalize_map_name`) and Quick Play win rates summed over its 1v1 and team leaderboards (cached 15 min; requests go through a sliding-window limiter because aoe2companion allows 16 requests/10 s, and posts wait at most `QUICKPLAY_STATS_WAIT_SECONDS` before posting without them and editing them in later) (Relic has no Quick Play leaderboard), and in-game player numbers (colours 1–8; Relic lobbies have no slots), which the bot polls for after a match starts and then adds to the post, and match results (`finished`, per-player `won`).
- `matchbot/steam` — `SteamClientWithout2FA` (wraps `steam[client]`; logs in with a refresh token from `SteamAuthenticationService` because Steam rejects the library's plain-password CM logon with `InvalidPassword`). The library is gevent-based and blocking, so the bot only uses it through `SteamThread.run(func, *args)` (`func(client, *args)` on a dedicated thread; the client is created there too, because gevent objects are bound to their creating thread). Its unbounded waits are bounded: `_pre_login` overrides the library's (whose `connect()` retries forever), `TCPConnectionWithTimeout` gives up a CM connect after 10 s. A login against unreachable servers fails in ~30 s; before this, an internet outage froze the whole event loop for hours.

## Persistence and runtime files

- State is a JSON dataclass (`AoeMatchBotDatabase`) at `<data dir>/cache/aoe_matchbot_database.json` (a database from before the rename, `aoe_matchalyzer_database.json`, is moved there on startup): subscribed channel IDs, tracked SteamID64s, the last 20 analysed match IDs, per-channel `elo_max_diff` and `smurf_max_diff`, and the global `banlist` (Relic profile ID → name, SteamID64, comment).
- Logs go to stdout and `<data dir>/logs/aoe_matchbot_<timestamp>.log` (root logger set up in `__main__`, level `MATCHBOT_LOG_LEVEL`, default INFO; `bot.run(log_handler=None)`). INFO: posted matches (`ui.match_summary`), start/dodge, alerts, every slash command with its reply (logged in `_reply`); INFO posts also say how long after the lobby was first seen they went out; DEBUG: auto-deletes, late edits, scan durations (WARNING above `LOBBY_SCAN_SLOW_SECONDS`), first sighting of tracked players' lobbies.

## Notes

- `APP_CLIENT_LIB_VER` and the version fields in `platformlogin` are hardcoded; login has worked with them across game patches. If Relic ever starts rejecting stale values, that is where to look.
- Game-mode names come from a hardcoded `GAME_MODE_ID_TO_NAME` map in `matchbot/ui`.
